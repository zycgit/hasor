# v5.3.0 (In Development)

## Scope

- Web, Config, Boot Loader, and documentation.

## Changes

- New Features
  - Add `HandlerInterceptor` and `WebApiBinder.bindInterceptor(...)`, with pre-handlers in registration order and post-handlers and completion callbacks in reverse order.
  - Add `ExceptionHandler` and `WebApiBinder.addExceptionHandler(...)`, selecting the most specific registered exception type.
  - Add `Invoker.setSkipRender()` and `isSkipRender()` to skip rendering for the current request without allowing the state to be reset.
  - Add Config `WebMvcConfigurer.addInterceptors(...)` and `@Exception` factory registration, reusing Bean dependency injection, scopes, and lifecycle management.
- Bug Fixes
  - Render exception handler results from void Actions.
  - Clear the request-parameter cache when request processing ends.
  - Fix a null-pointer error when resolving the content type without a matched Action.
- Improvements
  - Resolve the final MVC result before deciding whether to render; normal return values, post-handler results, and exception handler results share one rendering path.
  - Load interceptor and exception handler registrations when the Web context initializes, avoiding repeated container lookups per request.
  - Separate asynchronous error handling from completion: call `complete()` on success and `dispatch()` on failure. See the asynchronous request guide for propagation limitations.
  - Relocate and trim Cobble in Boot Loader, embedding only the required logging classes independently of the application's version. Project dependencies and published artifacts use the same self-contained Loader JAR.
  - Add tests for MVC, exception handling, rendering control, and Loader dependency isolation, plus MVC integration cases for Jetty, Tomcat, and Undertow.

## Upgrade Notes

- Custom `Invoker` implementations must implement `setSkipRender()` and `isSkipRender()`. Custom `WebApiBinder` implementations must implement MVC `bindInterceptor(...)` and `addExceptionHandler(...)`. Their wrapper classes already delegate these methods.
- Extensions calling `RenderProcessor` directly must call `initInvoker(invoker)` before MVC invocation, then pass the final result to `invoke(invoker, finalResult)` instead of passing an invocation chain.
- In custom `AsyncInvocationWorker` implementations, `doWorkWhenError(...)` only handles errors; `finish(boolean)` owns completion and redispatch. Avoid duplicate `complete()` or `dispatch()` calls.
- See [asynchronous requests](../../guides/webmvc/j2ee/async.md) for response-output and exception-propagation limitations.
